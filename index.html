Abstract

Documentation has had three main readers: developers, architects and support engineers. The EU AI Act adds readers who use documentation as evidence. A provider of a general-purpose AI model must keep its technical documentation current, give it to the AI Office and national authorities on request, and give downstream providers the information they need6. Inside the company, a compliance lead must show the same evidence before anyone asks. These readers don't ask how to use a model. They ask for proof: for this version, from this source, approved by this person.

The technical writing team already holds that proof. A DITA source in Git has one source of truth, a version history, named reviewers and audience profiling. AEGIS (AI Evidence and Governance Integrity System) is an agent that turns that source into an evidence pack. Each requirement is a DITA topic. A relationship table links each requirement to the topics that answer it. Four deterministic checks prove that each link is covered, current, approved and consistent. Gemini proposes a link only where a requirement has none. A compliance lead releases the pack, and AEGIS seals it in a Cloud Storage bucket with a locked retention policy.

The first AEGIS design was a governance platform for a fictional asset manager, with five agents and an EU AI Act risk classifier31. This version keeps its evidence bundle and its human escalation. It drops risk classification, because deciding whether an obligation applies is a legal decision, not a documentation decision.

§1 Client Brief

The client is Google's AI model documentation, together with the Cloud TPU documentation that describes the hardware the models train on. Google signed the EU general-purpose AI Code of Practice in July 20251214. The sample content is the public Gemma 4 model card2, the Gemma 3 model card3 and the Gemma overview page4.

It is a good test for four reasons. A model card is the public document closest to what the regulation asks for, so its sections map to most items in Annex XI. It has real gaps and drift to find (§2.1). It is published under CC BY 4.0, so it can be adapted1. And it raises a real applicability question: Gemma 4 is released under Apache 2.02, and Article 53(2) exempts some open-source models from parts of the documentation duty6. AEGIS doesn't answer that question. It records who answered it, and when.

1.2 Regulation in brief

Two frameworks set the scope. The EU AI Act (Regulation (EU) 2024/1689) is binding law5. The Digital Omnibus on AI, Regulation (EU) 2026/1744, moved the high-risk dates later10. The obligations for general-purpose AI models did not move. They have applied since 2 August 2025, and the AI Office can enforce them with fines from 2 August 202611. The NIST AI Risk Management Framework is voluntary. NIST is revising it, and has not given a release date for the new version15.

Scope
AEGIS proves that evidence exists, is current, was approved and is consistent. It doesn't decide whether an obligation applies, and it doesn't judge whether the evidence is legally enough. Those are decisions for the compliance lead and legal counsel. AEGIS records each decision with a name and a date, like any other item.

§2 Problem Statement

When the AI Office or a downstream provider asks for model documentation, someone has to put a pack together. Today that pack is built by hand from published pages, spreadsheets and email. It is slow, and it can't show which version of each statement was sent or who approved it. Article 101 allows fines for information that is incorrect, incomplete or misleading9, so a pack that can't prove its own accuracy is a cost, not only an effort.

A real example
The Gemma 4 model card describes language support twice. The introduction says the model supports over 140 languages. The capabilities section says "Out-of-the-box support for 35+ languages, pre-trained on 140+ languages"2. Both can be true, because they measure different things. A pack built by copying must pick one sentence, from one page, on one date, and it records none of those choices. The same page also carries a notice that the documentation is deprecated and has moved to gemma.ai. In a DITA source the two numbers are two keys with two labels, and the move is a commit with a date.

The cost is mostly people's time. Figure 6 models one authority pack for one model, built by hand and built by AEGIS. Most of the manual time goes to chasing owners and confirming approvals, which is exactly what Git already records.

§4 User Stories

Each story has acceptance criteria that a tool or check in §5 tests.

US-1 · Documentation lead
As the documentation lead, I want each pack built from the source with its hours and model cost logged, so that I can show the time it saves.
Accepted when: seal_pack writes one register row per pack with build time, model calls and cost; review time comes from pull request timestamps.
US-2 · Technical writer
As the Gemma writer, I want each requirement linked to my topics in the map, so that I answer compliance questions by keeping the source current.
Accepted when: check_coverage reads only the relationship table; a topic older than the current model version shows as stale in check_currency.
US-3 · Information architect
As the information architect, I want every new requirement link to arrive as a pull request, so that no link reaches a pack without my review.
Accepted when: propose_mapping writes only to a branch; the evidence map has her as code owner; the agent's account can't approve.
US-4 · Research engineer
As the research engineer, I want confidential training facts to reach only the authority pack, so that they never appear in public output.
Accepted when: topics with audience="authority" are absent from the public and downstream builds; check_consistency fails the build if an authority-only key resolves in either.
US-5 · Compliance lead
As the compliance lead, I want each item in a pack traced to a commit, a date and an approver, so that what I send is complete and correct.
Accepted when: check_approval passes for every item; the manifest lists commit, revised date and approver for each requirement; seal_pack refuses a pack she hasn't released.
US-6 · Lena, reader
As an assessor, I want the pack to show the model version and date of each statement, so that I can check it against the model on the market.
Accepted when: each manifest item carries model-version and a revised date, and check_currency passes.
US-7 · Priya, reader
As a downstream provider, I want one pack with only the Annex XII items, so that I can meet my own obligations quickly.
Accepted when: the downstream build passes check_coverage for all 11 Annex XII requirements, and the pack is ready within one working day.

§5 Proposed Design

AEGIS v0.1 is an agent built with Agent Development Kit (ADK), Google's open-source agent framework22. Plain Python tools, called through function calling24, read the source, run the checks and build the pack. Gemini 3.8 Flash (gemini-3.8-flash)23 has one job. When a requirement has no evidence linked to it, Gemini proposes a link by filling a JSON Schema with structured output25. The checks decide pass or fail. The agent can't approve a link, release a pack or change a topic.

5.1 How it works

A compliance lead opens an issue for a request: who asked, which requirement set and which audience. AEGIS reads three inputs that already exist: the requirement map, the DITA source and the Git history. It runs four checks, asks Gemini only about requirements with no evidence, builds the pack with DITA-OT and opens a review. When the compliance lead releases the pack, AEGIS seals it. Figure 9 is the same context as Figure 1, with AEGIS added.

The DITA source is now on the evidence path. The model sits beside the checks, not in front of them. Its only output is a proposed link, and a person approves it before it counts. When the link pull request merges, AEGIS runs again.

5.2 Governance in DITA

AEGIS adds no new format. It uses four DITA 1.3 features that the team already knows. DITA 1.3 is the current OASIS standard, and DITA-OT 4.4 only previews DITA 2.019, so the design targets 1.3. Requirements become topics, links become a relationship table, evidence topics carry their dates in the prolog, and DITAVAL profiles decide which reader gets which topics.

5.3 Four checks

The checks are plain code. They give the same answer every time, and they decide whether a pack can be released. Each writes its result into the manifest, so the result becomes part of the evidence.

CheckPasses whenFails whenWrites
check_coverageEvery requirement in the set has at least one evidence topic that survives the pack's profileA row is empty, or its only evidence is removed by the profileCoverage table
check_currencyEach evidence topic was revised on or after the model version date, or holds only key references whose keys changed in an approved commit after that dateA topic is older than the model version and contains literal valuesStale list
check_approvalThe last change to each topic merged through a pull request approved by a code owner who is not the author or the agent2830A direct push, a self-approval, or no approvalApprover for each item
check_consistencyEach specification value resolves from a key, keys resolve the same in every pack, and no authority-only key appears in the public or downstream buildA literal value conflicts with a key, or authority content leaksConflict and leak list

5.4 Agent tools

The agent has ten tools. One calls the model. The pattern comes from the earlier projects in this series: plain tools give the same result every time, checks decide, and a person approves3233.

1. Load the requirement set load_requirements

Reads the requirement map for this request: Annex XI, Annex XII, or a set of NIST AI RMF subcategories. Each requirement is a topic with a key and the audience it is required for.

output: requirement keys, legal sources and required audiences

2. Read the evidence map read_evidence_map

Reads the relationship table, each evidence topic's prolog and keys, and the Git log and pull request reviews for each topic file.

output: requirement-to-topic links with dates, model version, commit and reviewers

3. Check coverage check_coverage check

Every requirement has evidence that survives the pack's DITAVAL profile.

output: covered requirements out of all requirements, with each empty row

4. Check currency check_currency check

Compares each topic's revised date and model version with the current model version date. A topic that holds only key references passes when its keys were updated in an approved commit.

output: current topics out of all topics, with each stale topic

5. Check approval check_approval check

Reads the pull request reviews from the GitHub API. The approver must be a code owner, must not be the author, and must not be the agent's account.

output: approver, role and date for each topic

6. Check consistency check_consistency check

Every value comes from a key. A key gives the same value in every pack. Authority-only keys never resolve in the public or downstream build.

output: conflicts and leaks, each with file and line

7. Propose a link propose_mapping model

Runs only for requirements with no evidence. Gemini reads the requirement topic and the titles and short descriptions of candidate topics, never their bodies. It returns a candidate topic ID from a list of real IDs, a reason and a confidence, or "none".

output: a relationship table change on a branch, or a gap note for the owner

8. Build the pack build_pack

Runs DITA-OT 4.4 on the map with the request's DITAVAL profile. Writes the PDF and HTML, the manifest (§5.8) and the coverage report.

output: pack files, manifest.json, report.html

9. Open the review open_review

Opens a pull request with the pack and the report. Assigns link proposals to the information architect and gaps to their owners. Asks the compliance lead to release. The agent can't approve.

output: review pull request and issues for each gap

10. Seal the pack seal_pack

Runs only after the compliance lead approves the release. Hashes each file with SHA-256, uploads the pack to a Cloud Storage bucket with a locked 10-year retention policy20, and writes one row to the BigQuery register.

output: object paths, manifest hash, register row

5.5 Agent loop

Checks run first. Gemini is called only for coverage gaps. Currency, approval and consistency failures go to people as gap notes, because only the owner can fix a stale topic or approve a change.

Figure 12
Agent loop for one request
A gap is never hidden. It is fixed in the source and the loop runs again, or it ships in the report with the compliance lead's decision and reason. Gemini never sees currency, approval or consistency failures.

The schema for propose_mapping is built fresh for each run, so the candidate list holds only topic IDs that exist in the map. Gemini can't link to a topic that isn't there. A proposal with a confidence under 0.6 becomes a gap note, not a pull request.

5.8 The manifest

The manifest is the part of the pack that turns documentation into evidence. It records, for each requirement, which topic answered it, from which commit, on which date and with whose approval. It also records every gap and the decision about it.

Data handling. The sample content is public, so the Gemini API free tier is acceptable for the POC. Content sent on the free tier is used to improve Google products, so a real deployment needs the paid tier26. AEGIS also limits what the model sees: propose_mapping sends only requirement text and the titles and short descriptions of candidate topics, never the body of an authority topic.

Known limits. AEGIS proves that evidence exists, is current, was approved and is consistent. It doesn't prove that the evidence is true. A locked retention policy can't be removed or shortened20, so the POC tests with a short unlocked policy first. Free-tier limits change over time21.
